# 樹木・Propの保存統合と復元順序

樹木・Propの拡張座標データを、地形・水流・所有・資源と同じ保存セッションへ統合しました。
全てのスナップショットを準備してからserializableDataStorageへ公開し、標準Serializeでは固定した投影配列を使用します。
保存が失敗したときは、樹木・Propと登録された追加データも以前の保存エントリーへ戻します。
ゲームが拒否する長さ16,711,680以上の追加byte配列は公開前に拒否します。

対象版のColossalManaged.DataSerializerを調べると、ルートを最初にキューへ追加し、
全オブジェクトのDeserializeを完了した後、先頭からAfterDeserializeを呼びます。
SimulationManager.Data.AfterDeserializeのPrefixへ復元処理を接続しました。
子ManagerがPrefabを再バインドしたり地区・公園内の樹木とPropを集計したりする前に、拡張座標と検索リストを復元します。
後続のManagers_UpdateDataでは二重復元しません。

この順序に依存するため、Assembly-CSharpに加えてColossalManagedのSHA256も照合します。
確認したColossalManagedは34701F61DEF31F5F9DF79D573CE19E0BC52575879BCC395D51B39F6D746A58B9です。
ルート・地形・水流・所有・資源・樹木・PropのDeserializeとルートAfterDeserializeには、例外時のセッション破棄を接続しました。

ISaveParticipantは追加Managerを保存セッションへ組み込むためのインターフェイスです。
ロード時には全参加者のデータ準備と対象検証を済ませてから、拡張データを反映します。
樹木・Propのデータが欠落・破損している場合や対象の配列形状が違う場合には、拡張地形を反映する前に拒否します。
拡張データのない旧保存では、標準座標を保持して検索リストを再構築します。

モックでは327,678個の有効な樹木・Propを含む保存・復元、集計前の座標復元、二重復元の防止、
保存失敗時の巻き戻し、追加Managerの事前検証失敗、破損・欠落した座標データ、ロード失敗後のリセットを確認しました。
実ゲームDLLのILではDeserialize/AfterDeserializeの呼び出し順、保存フックの組み込み、8個の例外処理接続を確認します。

Unity上の保存・再ロードは未検証です。電気・水道のセル・キュー保存、地区・区画・交通、
残る樹木・Prop参照、描画・ツール・境界、導入用パッチ管理は未完了で、CanActivateはfalseです。
この段階の成果は完成した100タイルMODではありません。
